# テストの基準
- テストの価値
  - 価値が高いのは、その関数の振る舞いや内部処理から逆算してバグを起こしそうな入力
  - 価値が低いのは、振る舞いに依存しない故意な入力(異常な入力・sqlインジェクションなど)
- セキュリティ、およびパフォーマンスに冠する特殊なテストは実装しないように
- テストは1関数or機能あたり最大で5個まで
- 実装について
  - 既存のテストやfixturesファイルは好きに書き換えて構わない。後方互換性的なものは一切無視するように

## モジュール区分
テストは以下の区分のルールに従いtestsモジュールのサブモジュールとして分類すること。
区分不可能なものは、testsモジュール直下への配置を行う。
上から順に高い優先度を持つ分類(迷ったら上選べ)。

- helper
  - Module for testing helper functions created for testing purposes.
  - tests直下にヘルパー関数を定義し、helperモジュールでそのヘルパー関数をテストする
- online
  - モックを使わず外部に通信が走るテストのモジュール
  - だがこのonlineテストは必ず通常のテスト時に実行されないようにすること
    - feature flagは"online"とすること
- {関数名}
  - 関数ごとにテストが**複数**ある場合はモジュールにまとめる
  - そうでない場合はtestsモジュール直下に配置
  - 関数や構造体、トレイトなど1つあたりのテスト数は最大でも5つまでに収めること
- tests
  - ルートモジュール
  - どこにも分類できない場合はここ

## 2. 価値の低いテスト

**削除対象:**
- 環境依存テスト: online featureの軽量テスト（学習価値低）
- 故意な異常入力テスト: test_parse_invalid_formats（パーサライブラリの責任）
- セキュリティテスト: test_store_article_links_with_special_characters SQLインジェクション対策（DB層の責任）
- 過剰なNull値テスト: test_null_value_handling（データベース制約で解決）
- 重複ロジックテスト: 同一パターンのバリデーション複数回実行

## 3. テスト名と実装の乖離

**リファクタ対象:**
- test_comprehensive_* - 実際は基本機能のテスト
- test_*_basic vs test_*_comprehensive - 機能差が不明確
- test_boundary_values_and_data_integrity - 複数責務を1つのテストに含有

## 4. 過剰に複雑なfixture

**削除・統合対象:**
- service_comprehensive.sql (80行) - service_basic.sqlで十分
- repository_comprehensive.sql - 重複データ大量
- repository_edge_cases.sql - 特殊ケース過剰
- 同一パターンのfixture複数（service_*, repository_*系）
